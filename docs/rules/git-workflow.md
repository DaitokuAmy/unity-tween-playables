# Gitワークフロールール

この文書を、このリポジトリにおけるコミットおよびリリースタグの正式なルールとします。

## コミットの分割単位

- 各コミットは、個別にレビューおよび取り消しができる、単一のまとまった目的を持たせてください。
- 実装を直接検証または説明するテストとドキュメントは、その実装と同じコミットに含めてください。
- 無関係なリファクタリング、フォーマットのみの変更、生成ファイル、依存関係の更新、動作変更は、それぞれ別のコミットに分けてください。
- 明示的なパスまたはハンクを指定してステージし、コミットの前にステージ済みの差分を確認してください。
- 既存の変更や、作業対象と無関係なワーキングツリーの変更をコミットに含めないでください。
- 明示的な指示がない限り、既存コミットの書き換え、フックの回避、破壊的なクリーンアップを行わないでください。

## コミットメッセージ

次の形式を使用してください。

```text
[type] 簡潔な要約
```

要約は命令形で具体的に記述し、末尾に句点を付けないでください。変更内容に適用できる最も限定的な種類を選択してください。

- `[feat]`: 後方互換性のある、利用者向け機能を追加する変更。
- `[fix]`: 誤った動作を修正する変更。
- `[refactor]`: 意図した動作を変えずにコード構造を整理する変更。
- `[test]`: 本番コードの動作を変えずにテストを追加または変更する作業。
- `[docs]`: ドキュメントのみの変更。
- `[build]`: ビルド、パッケージ、依存関係、リリース設定の変更。
- `[chore]`: 上記のいずれにも該当しないリポジトリ保守作業。
- `[release]`: リリースに伴うパッケージバージョンの更新。

例:

```text
[refactor] Luaステートの所有権管理を単純化
[fix] ドメインリロード時にコールバックを保持
[release] パッケージバージョンを0.8.1に更新
```

## 検証とプッシュ

- コミット前に `git diff --cached --check` を実行し、ステージ済みの差分全体を確認してください。
- ステージした変更に必要な検証を実行し、実行できなかった検証がある場合は報告してください。
- 設定済みのアップストリームへ通常のプッシュを行ってください。通常のコミット作業やリリース作業では、force pushを行わないでください。
- プッシュは独立した外部操作です。ユーザーがプッシュを依頼した場合、またはパッケージリリースのようにプッシュを明示的に含むワークフローを実行する場合にのみ行ってください。

## パッケージのリリースタグ

- リリースタグは `Packages/com.daitokuamy.unityluasystem/package.json` の `version` と完全に一致させてください。
- `0.8.0` のような、数値のみのSemantic Versioning形式を使用してください。先頭に `v` を付けないでください。
- `git tag -a <version> -m "Release <version>"` を使用して、注釈付きタグを作成してください。
- リリースコミットの検証が成功し、ブランチのプッシュが完了した後にのみタグを作成してください。
- タグは、同じバージョンを設定したマニフェストを含むリリースコミットを指すようにしてください。
- 既存のローカルタグまたはリモートタグを移動、置換、再利用しないでください。
- 対象のタグを明示的にプッシュした後、リモートのブランチとタグが意図したコミットを指していることを確認してください。
